## 2. 引擎字段可用性核查

> 在设计前先把 `castSkill()` 实际消费的字段全部列清，避免设计出"引擎读不到"的技能。
> ⚠️ 下方**不标行号**——`index.html` 正在被 engineering-lead 并行修改，本次核查期间行号已漂移约 56 行。一律以**函数名**定位。

### 2.1 `castSkill()` 实际消费的字段（✅ 可用）

| 字段 | 生效条件 | 语义 |
|---|---|---|
| `type` | 必填 | `'dmg'` / `'dot'` / `'heal'` / `'buff'` / `'aura'` |
| `mult` | dmg / dot | 伤害倍率。**dmg 走 `mult+(lv−1)×0.08`；dot 不走（BUG-5）** |
| `magical` | dmg | `def.magical \|\| def.attr==='int'` → 用 `matk` 结算、扣 `mdef` |
| `hits` | dmg | 追加 `hits−1` 次独立结算（各自独立 命中/暴击/吸血）|
| `slow` / `slowTurns` | dmg | 目标 `spd` 衰减，`effSpd()` 消费 |
| `vuln` / `vulnTurns` | dmg | 目标受伤加成，`dealDamage()` 消费。**dot 分支强制 push（BUG-4）** |
| `turns` | dot / buff | dot 持续回合 / buff 持续回合 |
| `heal` | **仅 heal 型** | 回复 `maxHp × heal × (1+healEff)`。**dmg 型写了不生效（BUG-6）** |
| `val` | buff | 推入 `atkBoost` |
| `spdBoost` | buff | 推入 `spdBoost` |
| `shield` | **全类型通用尾部** | `a.shield += maxHp × shield`，任何 type 都生效 ✅ |
| `stun` / `stunTurns` | **全类型通用尾部** | 目标推入 `stun`，任何 type 都生效 ✅ |
| `cd` | 必填 | 按**行动次数**递减；`cost = 8 + cd×3`（`playerUnit()`）|
| `attr` / `weapons` | 选技过滤 | 禁咒统一 `null` / `null` |
| `icon` / `tier` / `desc` / `school` / `license` | 表现与叙事 | 不进公式 |

### 2.2 全局 stat 对技能的影响（✅ 可用）

| stat | 作用点 | 备注 |
|---|---|---|
| `skillDmg` | `power *= (1+skillDmg)` | **仅 dmg 型**。dot / heal / shield **不吃** |
| `eliteBossDmg` | `power *= (1+eliteBossDmg)`（目标为精英/Boss）| 仅 dmg 型 |
| `healEff` | heal 型回复量 | |
| `crit` / `critDmg` / `lifesteal` / `dmgReduce` | `dealDamage()` / `applyDamage()` | **dot 完全绕过这四项** |

### 2.3 ❌ 不存在的字段（设计中已全部规避）

`pierce` · `ignoreDef`（仅存在于未录 `preDamage` 钩子的 ctx，不是 SKILLS 字段）· `aoe` / `targets`（引擎单目标）· `resist` / `element`（§3.6 裁决：学派不进公式）· `execute` / `threshold`。

> ✅ **结论**：§4 的 7 本禁咒共用 `type / mult / magical / hits / cd / turns / vuln / vulnTurns / slow / slowTurns / stun / stunTurns / shield / heal` 共 14 个字段，**全部已被 `castSkill()` 消费，新增字段数 = 0**。

### 2.4 🆕 v1.1 复查：三处引擎现状变更（affix-impl 已落地 05b）

| 项 | 现状 | 对本文的影响 |
|---|---|---|
| **`cdr` 已实装** | `playerUnit()` 产出 `cdBase = max(1, ceil(cd/(1+cdr)))`；`castSkill()` 用 `sk.cd = sk.cdBase ?? def.cd`；上限 `AFFIX_CAPS.cdr = 0.50` | ✅ 全部 7 本自动受益；`great_seal` cd9 → cd6，**RB4 消解** |
| **未录「赋予」已实装** | `syncMythicSkills()`：装备未录时若 `!G.player.skills[mythic.skill]` 则置 1 级 | ✅ §6.3 的 `bookEcho` 判定前提成立。⚠️ **但会自动学会禁咒**，与 §8 携带上限产生交互，见 §8.4 |

## 3. 设计约束的机制落实

### 3.1 方差红线（C3）

**判定标准**：一个效果是否让"同一套配装打同一个敌人"产生**胜/负两种结果**。

| 机制 | 裁决 | 理由 |
|---|---|---|
| 概率闪避 / 格挡 | 🔴 **禁用** | 直接方差源。05b §5 已把 POE 的格挡/法术格挡整族 DROP，本文保持一致 |
| 概率触发型 rider（"25% 概率眩晕"）| 🔴 **禁用** | 同上。**7 本禁咒的 rider 全部为 100% 触发** |
| 确定性减伤（`dmgReduce`）| 🟠 **不由禁咒提供** | 按 team-lead 口径执行。减伤是**词缀的职能**（05b §4 `sf_ward` 族），禁咒不抢 |
| **护盾（`shield`）** | ✅ **保留** | 护盾**不是减伤**：它是一次性、定量、可在出击前精确算出的 HP 缓冲（`maxHp × shield`），**零方差**。既有 `uni_guard` / `ice_barrier` 已在用 |
| 命中 / 暴击 | ✅ 保留 | 引擎既有全局机制，非本设计引入；且 `hits` 多段技**降低**方差（见 §5.3）|

### 3.2 无永久跨战叠加（C4）

7 本禁咒的**全部**状态都写入 `actor.buffs[]` / `actor.shield`。
`playerUnit()` 每场战斗重建 unit 对象（`buffs:[], shield:0`），**天然清零，无需任何 `battleStart` 钩子**。

> 对比：这正是 05b §6 把未录 ④`myth_forge_hammer`（`G.player.mythicStr += 1`）和 ⑧`myth_dragon_brand`（`G.player.mythicHp += 2`）全量重设计的原因——那两个写进了 `G.player.*`（进存档、跨战斗、无上界）。
> **本文 7 本禁咒不碰 `G.player.*` 的任何数值字段**，仅读 `G.player.skills[id]` 取等级。

### 3.3 反主导策略：禁咒的强度身份

🔴 **红线：主导策略**。禁咒 `weapons:null` = 任何 build 都能用。若它们同时**伤害也最高**，玩家的最优解将永远是"堆满 10 本禁咒、无视武器系技能"，直接击穿 GDD 03 **G1（换武器 = 换玩法）**。

**因此定死禁咒的强度身份：**

> **禁咒 = 低倍率密度 + 强 rider + 不挑武器。**
> 单位时间伤害**低于**同阶本系技能；它的价值在于"**通用性**"与"**rider 的战术效果**"，而不是 DPS。

数据佐证（§5 完整表）：既有 `boundary_wrath` 密度 0.558、`silent_hymn` 0.441，而中阶本系技 `piercing_shot` / `frost_nova` 密度 0.644。**既有设计已经是这个身份**，本文 7 本严格延续。

## 5. 强度校验

### 5.1 倍率密度算法

```
非 dot：密度 = mult × hits × K_def × K_crit / cd
dot   ：密度 = mult × turns / cd            （dot 绕过 def / crit / skillDmg / dmgReduce / shield）

K_def  = 1 − DEF/(DEF+220) = 0.572   （取 tier9 Boss DEF=165 的终局工况）
K_crit = 2.25                         （终局暴击率×暴伤 + skillDmg 的综合放大，仅非 dot 享有）
∴ 非 dot 系数 = 0.572 × 2.25 = 1.287
```

> ⚠️ **dot 是真实伤害**：`processStartBuffs()` 直接 `u.hp -= Math.round(buf.dmg)`，**不过 `dealDamage()`**，因此不吃防御衰减、不吃 `dmgReduce`、不被 `shield` 吸收、不能暴击、不吃 `skillDmg`。这是 dot 密度算法不同的原因，也是 §7.4 balance 风险的来源。

## 6. 与「敕令共鸣」未录体系的联动接口

### 6.1 现状

GDD 04b §9.4 定义：每件未录绑定一个 `mythic.skill`，装上即「赋予 + 强化 + 改写」。
本期 7 件新未录绑定的是**既有通用/属性技能**（`berserk`/`chain_lightning`/`uni_guard`/`heal_light`/`sunder_strike`/`uni_strike`/`aura_cast`），正是因为 R12 的 book 当时还没设计。

### 6.2 ❌ 不采用的方案：把 `mythic.skill` 改绑到同源 book

技术上**零成本**（`applyMythic` 已按 skillId 分发，改一个数据字段即可），但**设计上不可取**：

> 这会让未录的效果依赖"**恰好同时拥有**该 Boss 的未录（5%）**和**它的书（5%）"。
> GDD 04b §9.4 已明确否决过套装式联动，理由是"对放置游戏的单次掉落体验不友好"（R11）。
> 改绑之后，玩家掉到未录却发现它**不生效**——这是放置游戏最糟糕的反馈。

### 6.3 ✅ 采用的方案：`mythic.bookEcho`（可选增益，非必要条件）

**保持现有 `mythic.skill` 绑定完全不变**，仅新增一个**可选**字段：

```js
mythic: {
  skill:'berserk',                    // ← 不变。未录单独持有时 100% 完整生效
  desc:'…', cost:'…',
  bookEcho:{                          // 🆕 可选。同时拥有本 Boss 的 book 且已学 ≥1 级时追加
    book:'forge_seal',
    desc:'同源共鸣：…'                //   ⏸️ 本轮不定稿，见下
  }
}
```

**判定逻辑（纯数据，零新钩子）**：
```
hasEcho = !!(item.mythic.bookEcho && (G.player.skills[item.mythic.bookEcho.book] || 0) > 0)
```
在 `applyMythic()` 内取一次即可，不需要新的 hook 事件。

**为什么这个接口是对的**：
- 只有未录 → **完整体验**，不残废 ✅（尊重 R11 的批评）
- 只有 book → **一本可用的禁咒**，不残废 ✅
- 两者都有 → **额外一层**，这是给深度玩家的奖励，不是门槛 ✅

### 6.4 本轮留白

7 条 `bookEcho.desc` 的**具体内容本轮不定稿**，原因：共鸣效果的强度必须建立在"玩家能同时拿到两者的概率"之上，而这取决于 **§10 的学习机制口径**（消耗品可叠级 vs 装备唯一）。口径定了我再补。

**已确定的红线（无论口径如何）**：
- 共鸣**不得**引入永久跨战叠加（同 §3.2）
- 共鸣**不得**引入概率触发（同 §3.1）
- 共鸣增益幅度 **≤ 未录本体效果的 40%**，保证"只有未录"仍是主体

## 7. 🔴 引擎缺陷（阻塞 / 影响本设计）

> 以下 4 项**均为现网既有缺陷，非本设计引入**，但会直接决定 7 本禁咒能否正常工作。
> 已同步 engineering-lead。

### 7.1 🔴 BUG-4 · dot 型技能缺 `vuln` → 战斗永久软锁（**严重**）

**位置**：`castSkill()` 的 `type==='dot'` 分支
```js
t.buffs.push({type:'dot',  dmg:a.atk*def.mult, turns:def.turns});
t.buffs.push({type:'vuln', val:def.vuln,       turns:def.turns});   // ← 无条件 push
```
**链路**：
1. `poison_edge`（淬毒刃，敏捷系基础技，**普通怪就掉**）**没有 `vuln` 字段** → push `{val: undefined}`
2. `dealDamage()`：`const vuln = t.buffs.find(x=>x.type==='vuln'&&x.turns>0); if(vuln) dmg = Math.round(dmg*(1+vuln.val));`
3. `1 + undefined` → `NaN` → `Math.round(NaN)` → `NaN`
4. `applyDamage(t, NaN)` → `t.hp -= NaN` → **`t.hp = NaN`**
5. `checkBattleEnd()`：`e.hp <= 0` 对 `NaN` 恒为 `false` → **敌人永远不死，战斗永不结束**

**影响面**：任何敏捷 build 学会淬毒刃后，**首次施放即软锁当前战斗**。这是 P0。

**修法**（2 行）：
```js
if(def.vuln) t.buffs.push({type:'vuln', val:def.vuln, turns:def.vulnTurns||def.turns});
```
外加 `dealDamage` 兜底：`dmg = Math.round(dmg * (1 + (vuln.val||0)));`

### 7.2 🔴 BUG-5 · dot 型技能不吃技能等级

**位置**：同分支，`dmg: a.atk * def.mult` —— 用的是 `def.mult`，而不是上方已算好的局部变量 `mult = def.mult + (lv−1)*0.08`。

**后果**：`poison_edge`、`blackmarket_toxin`、以及本文的 `strike_from_record`，**1 级和 10 级伤害完全一致**。玩家把书叠到 10 级发现毫无变化。

**修法**（1 处改名）：`dmg: a.atk * mult`。

### 7.3 🟠 BUG-6 · `dmg` 型技能的 `heal` 字段完全不生效

**位置**：`castSkill()` —— `heal` 仅在 `type==='heal'` 分支处理；而 `shield` / `stun` 在**通用尾部**处理。

**后果**：既有 `silent_hymn`（无声圣咏）的 `heal:0.10` **从上线起就没回过血**，但 `desc` 写着"并回复10%生命"——**文案与行为不符**。本文的 `inkwell_draw` 同样受影响。

**修法**（约 3 行）：把 heal 提到通用尾部，与 `shield`/`stun` 并列：
```js
if(def.heal && def.type!=='heal' && !a.noHeal){
  a.hp = Math.min(a.maxHp, a.hp + Math.round(a.maxHp*def.heal*(1+(a.healEff||0))));
}
```
> ✅ 修完 `silent_hymn` 自动恢复，属于**顺带修复既有内容**。

### 7.4 🟠 BUG-7 · `vuln` 取"最先施加"而非"最大值"

**位置**：`dealDamage()` —— `t.buffs.find(x => x.type==='vuln' && x.turns>0)`，`find` 取**数组第一个**。

**后果**：多个易伤源共存时，**只有最早 push 的那个生效**，且**不叠加、不取大**。
对本设计是直接伤害：玩家先放 tier5 `strike_from_record`（`vuln 0.22`），再放 tier9 `true_name`（`vuln 0.35`）→ **0.35 被 0.22 吞掉**，最高阶禁咒的核心 rider 失效。

**修法**（建议取当前生效中的最大值）：
```js
const vs = t.buffs.filter(x=>x.type==='vuln' && x.turns>0);
if(vs.length) dmg = Math.round(dmg * (1 + Math.max(...vs.map(v=>v.val||0))));
```
> 取 max 而非叠加，是为了守住 §3.3 的强度天花板——叠加会让"多带几本禁咒"变成主导策略。

### 7.5 🟡 既有失衡 · 禁咒只吃 `atk`，智力 build 收益腰斩

**现状**：3 本既有禁咒全部 `magical` 缺省 → 走 `a.atk`。而智力 build 的 `atk = str×2.4 + agi×0.6` 极低。

**建议（1 行，可选）**：禁咒是"抢来的违禁法术，它不问你是谁、不问你拿什么武器"——让它**按 `max(atk, matk)` 结算**：
```js
let power = (def.tier==='boss' ? Math.max(a.atk, a.matk) : (magical ? a.matk : a.atk)) * mult;
```
`magical` 字段则保留其**防御通道**语义（扣 `mdef` 还是 `def`）。
> 这个改动机制上干净、叙事上完美，且**一次性修好既有 3 本**。若不采纳，§5.4 的 4:3 配比是最低限度补偿。**需 team-lead 拍板。**

### 7.6 🟡 balance · dot 是真实伤害，在高防目标上超模

`processStartBuffs()` 直接扣血，绕过 `def` / `dmgReduce` / `shield` / 暴击 / `skillDmg`。
在 tier9 Boss（DEF 165，衰减 43%）面前，既有 `blackmarket_toxin` 的等效密度 **0.700**，是全池最高（见 §5.2）。**BUG-5 修复后 dot 开始吃等级，会进一步放大。**

**本文的应对**：`strike_from_record` 已按此**下调**（`mult 0.80` / `cd 7`，密度 0.571，低于 `blackmarket_toxin`）。
**建议但不强求**：给 dot 加一道轻量防御衰减（如 `dmg × (1 − DEF/(DEF+660))`，即正常衰减的 1/3），保留"dot 克高防"的定位但不失控。**这是既有平衡问题，超出 #13 范围，登记备查。**

## 8. 🟠 支柱漂移风险：禁咒无携带上限

### 8.1 问题

`playerUnit()` 从 `G.player.skills` **全量**构建技能列表，**没有携带数量上限**。
本文交付后，`weapons:null` 的技能将达到 **13 个**（10 本禁咒 + 3 个通用技）。

一个刷满内容的玩家会同时持有 10 本禁咒，全部 `weapons:null`、全部参与 `ready` 排序。后果：
1. **行动经济 100% 被技能占满**，普通攻击几乎不再出现；
2. **换武器不再改变技能池**——本系技能被禁咒挤到几乎不释放；
3. 🔴 **直接稀释 GDD 03 G1「换武器 = 换玩法」**，这是本作的**第一支柱**。

> 这属于 **支柱漂移**红线。它不是本文引入的（既有 3 本已有同样性质），但本文把规模从 3 放大到 10，**量变触发质变**。必须在落地前决策。

### 8.2 建议方案：禁咒携带上限 = 3（「越权」）

GDD 03 §3.6 结尾已经埋了钩子：
> "这也是 Later「**越权通缉度**」机制的数据基础——届时只需读这个已存在的字段（`license`）。"

**提前兑现它**：

| 项 | 规格 |
|---|---|
| 规则 | 玩家可**学习**任意数量禁咒，但同时**启用**上限 **3 本** |
| 判定 | `playerUnit()` 构建 skills 时过滤：`tier==='boss'` 的技能只取玩家在技能面板勾选的前 3 个 |
| UI | 技能面板给 `tier:'boss'` 的条目加「启用 / 未启用」开关 + `3/3` 计数 |
| 叙事 | 「你能同时持有的违禁咒文是有数的。超过这个数，秘典庭会注意到你。」 |
| 工程量 | `playerUnit()` 加一个 filter + 存档加 `G.player.activeBossSkills:[]` + 面板一个开关 |

**为什么是 3**：既有 3 本禁咒的时代就是这个体量，玩家已经适应；且 3 本 × 平均密度 0.485 ≈ 1.46，仍低于本系 5 技的合计密度，保证武器系技能是主力。

**这同时解决了一个体验问题**：10 本全生效时，玩家无法预判"这回合会放哪个"——违反 G2。3 本上限让战斗重新可推演，而且**"带哪 3 本"本身变成一个 build 决策**，反而增加了深度（支柱一："你不操作战斗，你设计战斗"）。

### 8.3 备选（若不想加 UI）

按 `license` 硬限：`illicit`（私法）类最多同时生效 2 本，`restricted` 不限。工程更小但玩家不可控，**不推荐**。

> 🔴 **本项需 team-lead / 用户拍板。在拍板前，7 本禁咒的数值设计不受影响**——上限方案不改任何 §4 数值。
