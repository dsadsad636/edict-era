## 0. 图例与统计

**处置标记**

| 标记 | 含义 | 工程量 |
|---|---|---|
| ✅ **沿用** | 代码与数据结构不动，可能只改显示文案 | 极低 |
| 🔧 **改造** | 结构/字段沿用，**数据内容全换** | 低（填表） |
| 🆕 **新增** | 守夜人没有，需要新写 | 中–高 |
| 🔴 **移除** | 必须删除，否则违反硬约束 | 中（要拆干净） |
| ♻️ **重写** | 保留概念，但实现完全推翻 | 高 |

**统计总览**

| 处置 | 数量 | 占比 |
|---|---|---|
| ✅ 沿用 | 17 | 37% |
| 🔧 改造 | 18 | 39% |
| 🆕 新增 | 6 | 13% |
| 🔴 移除 | 3 | 7% |
| ♻️ 重写 | 2 | 4% |
| **合计** | **46** | — |

> 💡 **结论：79% 的系统是"沿用 + 改造"**，即绝大部分工作是填数据表和改文案，不是写新系统。这验证了"骨架复用"策略的可行性，也说明 MVP 的真实瓶颈在 **🔴 移除联机层** 和 **内容量产出**，不在系统开发。

## 🔴 G 组 · 必须移除（纯单机硬约束）

> ⚠️ **这是 MVP 的最高优先级与最大风险块。** 守夜人的联机层不是可选模块，它**深度嵌入**了存档路径、角色创建、战斗循环三处核心。不拆干净会导致：登录墙挡住玩家、存档写向不存在的服务器、战斗时反复 `fetch` 失败。

| # | 系统 | 源码符号 | 处置 | 层级 | 拆除难点 |
|---|---|---|---|---|---|
| G1 | **账号系统** | `Auth` 对象：`/api/register`、`/api/login`、`/api/me`、`/api/save`、`/api/load`、`/api/charname-check` | 🔴 移除 | **MVP** | 与 **A1 存档**、**A2 创角** 强耦合。移除后需保证本地存档路径唯一。<br>⚠️ **工程复核补正**：`Auth` 另有 **5 处静默 brick 运行时守卫**（本表初版漏报）——不处理会导致游戏静默卡死且不报错。详见 `docs/architecture/adr/ADR-004-Auth守卫剥离契约.md` |
| G2 | **WebSocket 联机层** | `MMO` 对象（**35 处引用**）、`ws`、`wsUrl()`、心跳 `setInterval`、聊天、在线列表、重连 `scheduleReconnect()` | 🔴 移除 | **MVP** | 引用分散（含 UI 层的在线状态显示）。<br>⚠️ **源码实测补正**：`startBattle` 的 **L2492 是联机真入口**，原文 `if (MMO && MMO.party && MMO.party.members && ...)`，**首 token 为裸 `MMO`**。删除 MMO 块后若残留该行，`startBattle` 每次抛 `ReferenceError`，**全部战斗直接不可用（硬崩，非静默）**。<br>👉 DoD 必须搜裸标识符 `\bMMO\b`，只清 `MMO.xxx` 会留下悬空引用 |
| G3 | **服务端协调组队战斗** | `startPartyBattle()`、`sendPB()`、`pb_action`、`b.partyMode`、`b.aggro`、`b.lootWinner`、`b._partyDmg` | 🔴 移除 | **MVP** | ⚠️ **最麻烦的一个**，风险等级 🔴 高。<br>**工程复核修正了本表初版的三个数字**：`partyMode` 实际渗透 **8 个函数 / 13 处**（初版写 5 处，低估）；`sendPB()` 实际 **5 处调用**（初版写 8+，高估）；**`unitAct` 零引用（初版为误报，勿动该函数）**。<br>🔴 **最危险的一处**：`castSkill()` L2708 的护盾计算行与 `sendPB()` 混写——删上报时若漏改，**护盾会静默失效且不报错**，战斗照常运行，只表现为玩家莫名暴毙。详见 `docs/architecture/00-singleplayer-migration.md` |
| G4 | **组队占位接口** | `Party = { isRemote, members }`、`tabParty()`、组队 UI 面板 | ♻️ **重写** | **V1** | 概念保留（队伍结构对 AI 佣兵有用），实现推翻。MVP 阶段先隐藏入口 |

> 📌 **给程基岩的提示**（经 team-lead 中转）：建议 G1–G3 作为**独立的第一个工程任务**完成并验证（"能离线打开、能创角、能存读档、能打完一场战斗，且断网无任何报错"），再开始内容替换。否则内容工作会建在会塌的地基上。

## 依赖排序 → Phase 2 GDD 目录

依赖规则：**上游未定，下游不能写**。例如词缀池未定就无法写装备生成，地图未定就无法写掉落表。

```
【第 0 波 · 地基，阻塞一切】
 └─ 0. 单机化改造（G1+G2+G3 移除 · A1 存档 · A2 创角）
        ⚠️ 这不是设计任务，是工程任务，但它阻塞所有内容验证

【第 1 波 · 角色底座】
 ├─ 1. 属性与角色成长（A3 A5 A6 A7）
 └─ 2. 出身系统（A4）              ← 依赖 1

【第 2 波 · 装备底座】
 ├─ 3. 稀有度与认证等级（B1）
 ├─ 4. 武器类型网格（B3）          ← 依赖 1（attr 绑定）
 ├─ 5. 护甲分型与阶位链（B4 B5 B6）
 └─ 6. 槽位基础值（B2 B7）

【第 3 波 · 装备内容】
 ├─ 7. 词缀池与命名生成（B8 B9 B10 B11）   ← 依赖 3,4,5,6
 └─ 8. 套装系统（B12）                      ← 依赖 5,7

【第 4 波 · 技能】
 └─ 9. 技能表与光环（C1 C2 C3 C4 C6）       ← 依赖 1,4（武器绑定）

【第 5 波 · 战斗】
 └─ 10. 战斗循环与结算（D1 D2 D3 D7 D8）    ← 依赖 1,7,9

【第 6 波 · 内容填充】
 ├─ 11. 怪物与五族群（D4 D5 D6）            ← 依赖 10
```
