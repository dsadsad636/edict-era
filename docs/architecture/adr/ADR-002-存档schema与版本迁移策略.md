## 1. 背景

### 1.1 前作现状（实测复核）

前作的存档"迁移"是一个叫 `applyCompat()` 的函数（L3582-3631，**50 行**），形态是**无版本号的防御式字段补齐**：

```js
function applyCompat(){
  if(!G.account) G.account={...};
  if(typeof G.player.str==='undefined'){ G.player.str=8; ... }
  if(typeof G.player.con==='undefined'){ G.player.con=8; }
  if(typeof G.player.spi==='undefined'){ G.player.spi=8; }
  if(typeof G.folds==='undefined') G.folds={};
  ...                                   // 共 30+ 个 if
  /* 锻造材料：旧档 p.materials 为数字，迁移为按品质分类的对象 */
  if(!G.player.materials || typeof G.player.materials!=='object'){...}
  /* 阶位命名分化（A方案）：旧档装备按新命名表重算名字 */
  try{ ...renameFix... }catch(e){}
  /* 武器重做：旧档 sword/axe/hammer 映射到新类名 */
  try{ const wmap={sword:'one_sword',...}; ... }catch(e){}
}
```

### 1.2 这套做法的四个致命问题

| # | 问题 | 后果 |
|---|---|---|
| **P1** | **无版本号，无法判断"这个存档是哪一代"** | 只能靠"字段存不存在"反推。一旦某次改动是**修改字段含义**而非**新增字段**（例如把 `crit` 从 0-1 小数改成 0-100 百分数），`typeof` 检测**完全无能为力** |
| **P2** | **每次加字段就加一个 `if`，函数无限膨胀** | 50 行只经历了一次大版本（`_v2`）。本作内容量更大、迭代更频繁，这个函数会长到几百行 |
| **P3** | **迁移顺序隐式且脆弱** | 30 个 `if` 的执行顺序是隐含契约。L3606 的 `itemUid` 续号依赖 L3598 的 `materials` 已被修好，但代码里**没有任何东西表达这个依赖** |
| **P4** | **无法测试、无法回滚** | 没有"从 v1 到 v2"这个可命名的单元，就无法单独验证某一步迁移 |
| **P5** | **失败被静默吞掉** | 两处 `try{...}catch(e){}` 完全不记录错误。迁移失败 = 存档静默损坏 |

### 1.3 本作的特殊性

- **本作从 0 开始**（`ver: 1`），前作存档**不迁移、不兼容**（`arcanum_*` 与 `nightwatch_*` 命名空间天然隔离）
- ✅ 这意味着我们有**一次性把地基打对的机会**——不需要背历史包袱
- ⚠️ 但也意味着**现在偷懒的代价会在 3 个月后才显现**

---

## 2. 决策

> ## 采用 **显式版本号 + 单向有序迁移链 + 契约化字段声明** 三件套。
> 一句话规则：**`G.ver` 是唯一的真相。加字段不写迁移，加字段改默认值必须写迁移。**

### 2.1 三个组成部分

```
┌─────────────────────────────────────────────────────────┐
│ ① SCHEMA_VERSION 常量  +  G.ver 字段                     │
│    存档头部第一个字段，永远是数字，永远只增不减           │
├─────────────────────────────────────────────────────────┤
│ ② MIGRATIONS 有序迁移链                                  │
│    MIGRATIONS = [                                        │
│      { from:1, to:2, desc:'...', up(g){...} },           │
│      { from:2, to:3, desc:'...', up(g){...} },           │
│    ]                                                     │
│    载入时从 g.ver 顺序执行到 SCHEMA_VERSION               │
├─────────────────────────────────────────────────────────┤
│ ③ DEFAULTS 默认值模板 + 深合并                            │
│    新增字段（不改语义）只需在 DEFAULTS 加一行，          │
│    无需写迁移函数 —— 这是消灭 applyCompat 的关键         │
└─────────────────────────────────────────────────────────┘
```

### 2.2 载入流程（严格顺序）

```
读取 localStorage 原始字符串
    ↓
JSON.parse            ── 失败 → 判定存档损坏，进入 §5 损坏处理
    ↓
读取 g.ver（缺失视为 0，判定为非法档）
    ↓
若 g.ver > SCHEMA_VERSION  → 🔴 拒绝加载（见 §4「未来存档」）
    ↓
逐条执行 MIGRATIONS 中 from >= g.ver 的迁移，每步后更新 g.ver
    ↓
deepMerge(DEFAULTS, g)    ── 补齐一切新增字段
    ↓
validateSave(g)           ── 结构断言，失败则报告并进入损坏处理
    ↓
Offline.compute(g, now)   ── 离线结算（见 02 文档）
    ↓
返回可用的 G
```

> 📌 **`deepMerge(DEFAULTS, g)` 这一步就替代了 `applyCompat()` 里 30 个 `if(typeof x==='undefined')`。**
> 加一个新字段的完整成本 = **在 `DEFAULTS` 里写一行**。不需要动迁移链、不需要动存档代码。

### 2.3 什么时候必须写迁移函数（判定规则，写在代码注释里）

| 改动类型 | 是否需要迁移 | 例 |
|---|---|---|
| 新增字段（有合理默认值） | ❌ **不需要**，只改 `DEFAULTS` | 加 `G.codex.seenItems` |
| 新增嵌套对象 | ❌ 不需要 | 加 `G.offline = {...}` |
| **重命名字段** | ✅ **需要** | `G.mapId` → `G.world.mapId` |
| **改变字段类型** | ✅ **需要** | `materials` 从 number → object |
| **改变字段语义/单位** | 🔴 **必须**（最危险，`typeof` 检测不出） | `crit` 从 0.05 改成 5 |
| **改变数据表 key** | ✅ **需要** | 印屑 key `common` → `lead` |
| 删除字段 | 🟡 建议（清理垃圾数据，非必需） | 删 `G.account` |
| 数值平衡调整（不改结构） | ❌ 不需要 | 词缀区间调整 |

> 🔴 **红线**：「改变字段语义」是唯一会**静默损坏存档**的类型。凡是这类改动，**必须**在迁移链里写一条，哪怕只是一行乘法。
> 我建议在 `MIGRATIONS` 数组上方放一段醒目注释复述这条规则。

### 2.4 迁移函数的四条纪律

| # | 纪律 | 理由 |
|---|---|---|
| D1 | **每条迁移只做一件事**，`desc` 用一句中文说清 | 可读、可单独回滚 |
| D2 | **迁移函数内禁止引用数据表常量** | 数据表会随版本变化。v2 的迁移若引用了 `SKILLS`，而 v5 时某个技能被删了，这条迁移就会在老存档上崩溃。**迁移必须只依赖它写就那一刻的字面量** |
| D3 | **迁移必须幂等或严格一次性** | 由 `g.ver` 保证只跑一次，但函数本身不应假设"一定只跑一次" |
| D4 | **迁移不得抛异常吞异常**——用 try/catch 包住，失败要**上报**不要**静默** | 修 P5 |

> ⚠️ **D2 是最容易违反的一条**，且违反后要几个月才暴露。前作 `applyCompat` L3620 的 `renameFix` 调用了 `equipName()`，而 `equipName()` 依赖 `ARMOR_TIERS_BY_TYPE` 数据表 —— **这正是 D2 的反例**。本作严格禁止。

## 3. Schema v1 定义

```
SCHEMA_VERSION = 1

DEFAULTS = {
  ver: 1,
  slot: 0,
  createdAt: 0, lastSaveAt: 0,
  player: {
    name:'', level:1, exp:0, expNext:60, origin:'',
    str:8, agi:8, con:8, int:8, spi:8, attrPoints:0,
    hp:200, mp:100, gold:50,
    materials:{}, equip:{...7槽:null}, flasks:{hp:null,mp:null},
    skills:{}, inventory:[]
  },
  world:  { mapId:0, mapTier:0, unlocked:0, encounter:0,
            eliteDone:false, bossDone:false, mapEliteAt:null, mapBossAt:null,
            autoChain:false },
  offline:{ lastActiveAt:0, lastSettleAt:0, monotonic:0, pending:null },
  codex:  { kills:{}, seenItems:{} },
  ui:     { navTab:'char', folds:{}, bagCat:'equip', autoDecompose:false }
}

MIGRATIONS = []        // v1 是初版，暂空。第一条迁移在 v1→v2 时写入
```

### 3.1 🔴 v1 阶段特别预留的三件事

即使 MVP 用不到，也**必须在 v1 就放进去**，否则以后加就要写迁移：

| 预留 | 理由 |
|---|---|
| `G.codex`（图鉴，H4） | system-breakdown H4 明确要求"MVP 需预留数据结构"。空对象成本为 0 |
| `G.offline`（离线收益） | MVP 就要做 |
| `G.ui.autoDecompose` | 支柱二的"一键分解低价值掉落"偏好 |

### 3.2 序列化规则

```
存档字符串 = JSON.stringify(G, (k,v) => k.startsWith('_') ? undefined : v)
```

`_` 前缀字段（`_battle` / `_battleTimer` / `_log` / `_lastLoot` / `_dirty`）**自动不入档**。
> ✅ 这条规则同时解决了 `01-main-architecture.md` §6 里"战斗日志占存档 57%"的容量问题，以及前作 L3630 手工清 `G.battle` 的补丁。

## 4. 边界情况处理

| 情况 | 处理 | 理由 |
|---|---|---|
| `g.ver` 缺失 / 非数字 | 视为**损坏存档**，进入 §5 | 本作从 v1 起就一定有 ver，缺失说明被外部篡改或截断 |
| **`g.ver > SCHEMA_VERSION`（未来存档）** | 🔴 **拒绝加载**，提示「此存档来自更新版本的游戏，请更新后再打开」。**保留原档不覆盖** | 玩家可能在两台设备上跑不同版本（导入导出）。**降级加载必然丢数据**，静默丢数据比拒绝加载恶劣得多 |
| `JSON.parse` 失败 | 损坏处理 | |
| 迁移函数抛异常 | 🔴 **中止迁移，不写回**，保留原档，进入损坏处理并在控制台打印失败的迁移 `desc` | 半迁移的存档比没迁移的更糟 |
| `validateSave` 失败 | 同上 | |
| `QuotaExceededError` | 🔴 **不静默**。toast「存档空间不足，请分解部分物品」+ 控制台打印当前体积 | 修 P5 及前作 L3212 的静默 catch |

## 5. 存档损坏处理策略

> **原则：永远不要自动覆盖玩家的存档，哪怕它坏了。**

```
检测到损坏
    ↓
把原始字符串原封不动搬到 arcanum_corrupt_v1::<slot>::<timestamp>
    ↓
弹出面板：
   「槽位 N 的存档无法读取」
   [ 导出损坏存档（下载 .json，便于我人工修复） ]
   [ 新建角色（覆盖此槽） ]     ← 需二次确认
   [ 取消 ]
```

| 要点 | 说明 |
|---|---|
| ✅ 前作已有 `exportSave()` / `importSaveFromFile()`（L3159-3200） | **直接复用**，改成导出单槽而非整个命名空间 |
| ✅ 保留损坏副本 | 单机游戏没有客服，"导出发给作者"是唯一的救援通道 |
| ❌ 不做自动修复 | 猜测式修复会产生"看起来能玩但数值错乱"的存档，比明确报错糟糕得多 |

## 6. 后果

### 6.1 ✅ 正面

| # | 收益 |
|---|---|
| 1 | **加字段成本降到一行**（改 `DEFAULTS`），消灭 `applyCompat` 的 30 个 `if` |
| 2 | 迁移链是**可枚举、可读、可单独验证**的列表，取代隐式的执行顺序契约（修 P3） |
| 3 | 版本号让"改变字段语义"这类**最危险的改动变得可表达**（修 P1） |
| 4 | `_` 前缀规则顺带解决存档体积问题（-31 KB/档） |
| 5 | 拒绝降级加载 + 保留损坏副本，**杜绝静默丢档** |

### 6.2 ❌ 负面 / 成本

| # | 代价 | 缓解 |
|---|---|---|
| 1 | 需要写 `deepMerge` + `validateSave` + 迁移执行器，约 **80 行**（前作 `applyCompat` 是 50 行） | 一次性成本，之后每次加字段省一行 `if` |
| 2 | `deepMerge` 对数组的处理需要明确定义（数组是覆盖还是合并） | 🔴 **明确规定：数组一律整体覆盖，不合并**。`inventory` / `MIGRATIONS` 都不应被合并 |
| 3 | 纪律 D2（迁移不引用数据表）需要人工遵守，无工具强制 | 在 `MIGRATIONS` 上方写醒目注释；code review 检查项 |
| 4 | 开发期频繁改 schema 时，每次都要考虑"要不要写迁移" | 🟢 **开发期（未发布前）可直接改 `SCHEMA_VERSION=1` 不加迁移，清档重来**。迁移链的纪律**从首次公开发布那一刻开始生效**——这一点要写进注释 |

## 7. 备选方案

| 方案 | 描述 | 否决理由 |
|---|---|---|
| **A. 沿用前作 `applyCompat` 防御式补齐** | 每加字段加一个 `if(typeof x==='undefined')` | ❌ P1-P5 全部保留。**尤其 P1**：无法表达"字段语义变了"。前作只经历一次版本就写了 50 行，本作迭代更频繁 |
| **B. 只做版本号 + 大版本清档** | 有 `ver`，但不写迁移链，版本不匹配就让玩家重开 | ❌ 对**挂机 RPG** 是灾难。玩家的核心资产就是积累的进度，清档 = 劝退。<br>🟡 唯一可接受的场景是**未公开发布前**的开发期（已在 §6.2-4 采纳） |
| **C. 用 JSON Schema / Zod 做运行时校验** | 引入 schema 校验库 | ❌ 违反 ADR-001 单文件零依赖（要内联整个库）。<br>✅ **部分采纳**：`validateSave()` 手写一个 30 行的轻量结构断言，只查关键字段与类型，不追求完备 |
| **D. 双向迁移（up + down）** | 每条迁移同时支持升级和降级 | ❌ 成本翻倍，且降级**必然有信息损失**（新版本加的字段往哪去？）。§4 已决定直接拒绝加载未来存档，不需要 down |
| **E. 存档不用 JSON，用自定义紧凑格式** | 二进制/自定义分隔符，节省体积 | ❌ 牺牲可读性与可调试性。且 `01-main-architecture.md` §6.4 已论证：C1+C3+C4 之后容量余量充足（最坏 1.35 MB / 5 MB），**不需要**为体积做这种牺牲 |

## 8. 一页速查（贴在代码注释里）

```
════════════════════════════════════════════════════════════
 存档规则速查
════════════════════════════════════════════════════════════
 1. G.ver 是唯一真相。改 schema 先想"要不要写迁移"。
 2. 加字段（有默认值）      → 只改 DEFAULTS，不写迁移
 3. 改名/改类型/改语义/改key → 必须写迁移，无一例外
 4. 迁移函数禁止引用任何数据表常量（MONSTERS/SKILLS/...）
 5. 迁移只做一件事，desc 一句中文说清
 6. 未来版本存档 → 拒绝加载，绝不降级
 7. 损坏存档 → 备份原档 + 提供导出，绝不自动覆盖
 8. `_` 开头的字段不入存档
 9. 数组一律整体覆盖，不深合并
10. 迁移链纪律从「首次公开发布」开始生效；之前可自由清档
════════════════════════════════════════════════════════════
```
