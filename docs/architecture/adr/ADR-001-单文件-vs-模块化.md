| 项 | 值 |
|---|---|

---

## 1. 背景

《敕造纪元·持牌者》复用前作《守夜人·凋零纪元》的骨架。前作是单个 `index.html`，**4831 行**，包含 CSS（831 行）、HTML 骨架（141 行）、全部游戏逻辑（3541 行）、联机层（312 行）。

用户是独立开发者、中文母语、非专职程序员，已明确拍板：**本作继续单文件**。

本 ADR 的目的**不是论证该不该单文件**，而是：
1. 把这个决策的**真实代价**写下来，让它在未来变成"已知的痛"而不是"意外的痛"
2. 逐条给出**缓解手段**，并指明缓解手段失效时的**升级触发条件**

---

## 2. 决策

> ## 采用单文件 `index.html`。零构建、零依赖、零模块系统。
> 通过**注释分区约定 + 命名约定 + 折叠标记**替代语言级的模块边界。

---

## 3. 理由（记录用户与我共同认可的部分）

| # | 理由 | 我的评价 |
|---|---|---|
| 1 | **分发即文件**。发给朋友、传网盘、双击打开即玩，无需服务器、无需 `npm install` | ✅ 对纯单机网页游戏，这是**决定性优势**，不是妥协 |
| 2 | **零构建链**。没有 Vite/Webpack/Rollup 版本地狱，没有"三个月后构建挂了" | ✅ 对独立开发者，构建链的长期维护成本经常超过它节省的成本 |
| 3 | **前作已验证**。4831 行单文件确实做出了一个可玩的游戏 | ✅ 事实 |
| 4 | **AI 协作友好**。整个项目一次读入上下文，改动定位精确 | ✅ 这是 2026 年才成立的新理由，权重不低 |
| 5 | **调试直观**。DevTools Sources 里就是源码本身，无 sourcemap 中间层 | ✅ |

---

## 4. 后果

### 4.1 ✅ 正面

- 分发、部署、备份成本 ≈ 0
- 无构建产物与源码不一致的问题
- 无依赖供应链风险（前作 `index.html` 零第三方库）
- 全文搜索是**完备**的——不存在"这个符号在另一个文件里"

### 4.2 ❌ 负面（真实代价，逐条记录）

| # | 代价 | 严重度 | 已观察到的证据 |
|---|---|---|---|
| **N1** | **无编译期边界**。任何函数都能改任何全局变量，分层纯靠自律 | 🔴 高 | 前作实测已有 4 处分层违规（见 `01-main-architecture.md` §3.3）：`tickBattle` 直接调渲染、`applyPartyBuff` 在渲染区改状态、`mkMon()` 函数混在数据表、219 行 SVG 生成器夹在数据区 |
| **N2** | **无 Tree-shaking / 死代码检测**。删功能时残留分支不会被工具发现 | 🔴 高 | 这**正是** `00-singleplayer-migration.md` 存在的原因——联机层要靠人肉 grep 逐处清理，而非删一个 `import` |
| **N3** | **无类型系统**。字段名打错在运行时才炸 | 🟡 中 | 数据表有 14 张、字段数十个，填表打错字是最高频的错误来源 → **ADR-003 专门应对** |
| **N4** | **无单元测试框架**。没有 `import` 就没法在 Node 里跑函数 | 🟡 中 | 违背我的"验证驱动开发"原则 → 见 §5.4 缓解 |
| **N5** | **合并冲突不可分割**。多人协作时整个文件是一个冲突面 | 🟢 低 | 单人开发，暂不构成问题 |
| **N6** | **编辑器性能**。5000 行单文件的语法高亮、跳转、格式化会变慢 | 🟢 低 | 实测 VS Code 在 5000 行 HTML 上仍流畅 |
| **N7** | **加载时无法代码分割**。首屏必须下载全部 | 🟢 低 | 实测前作 294 KB，Gzip 后约 70 KB。**非问题** |

## 5. 缓解手段（每条代价对应一个可执行动作）

### 5.1 对 N1（无边界）→ **三级横幅 + 编号坐标 + 命名编码**

见 `01-main-architecture.md` §2.4。核心是：

| 手段 | 作用 |
|---|---|
| 三级横幅 `####` / `====` / `----` + 章节编号 `§3.2` | 让"层"在文本上可见、可引用、可跳转 |
| 文件顶部目录块 | 4900 行压缩成 12 行可视地图 |
| `//#region` 折叠标记 | 编辑器一键折叠整章 |
| 命名编码层级（`ALL_CAPS`=数据 / `Pascal`=模块 / `_x`=私有） | 看变量名就知道属于哪层、能不能改 |

### 5.2 对 N2（无死代码检测）→ **grep 断言清单**

把"应该不存在的符号"写成一份可执行的检查清单，每次重构后跑一遍：

```bash
# 单机化完成后，以下命中数必须全部为 0
grep -c "MMO\|Auth\|CloudSave\|sendPB\|partyMode\|CLOUD_ENDPOINT\|/api/" index.html
```

> 这就是 `00-singleplayer-migration.md` §5.3 R16/R17 的由来。
> **在没有编译器的世界里，grep 就是我们的编译器。** 把它制度化。

### 5.3 对 N3（无类型）→ **ADR-003 的字段契约 + 启动期校验器**

每张数据表头部写 `// 字段契约:` 注释块，并配一个 `validateData()` 在**开发模式启动时**遍历所有表校验必填字段与类型，控制台报「`MONSTERS.corrupt_golem` 缺少 `art.body`」。

> 详见 ADR-003。这是把"类型检查"从编译期挪到**启动期**——晚了几秒，但比"上线后才炸"早了几个月。

### 5.4 对 N4（无测试框架）→ **纯函数区 + 控制台自测函数**

| 手段 | 说明 |
|---|---|
| **§2 生成器层保持纯函数** | `genEquip` / `generateAffixes` / `rollRarity` / `dealDamage` 输入输出明确 |
| **内置 `__selftest()` 函数** | 在文件末尾放一个开发用自测函数，控制台调用即跑：批量调 `genEquip()` 1000 次断言无异常字段、`rollRarity` 分布是否符合权重、`dealDamage` 边界值等 |
| **随生产代码一起发布** | ~40 行，不影响玩家（不会被调用）。**不为了"干净"而删掉它**——删了就再也不会有人写回来 |

> ⚠️ 这**不等于**真正的单元测试。我承认这是妥协。但它把"完全无法验证"变成了"关键路径可验证"，在单文件约束下这是能达到的上界。

### 5.5 对 N1 的补充 → **提交粒度纪律**

单文件无法用"改了哪个文件"判断影响范围，因此**提交粒度必须更细**：
一次提交只动一个 `§N.M` 小节，commit message 首行写明章节编号，例如 `§3.4 castSkill: 移除 partyMode 分支`。
这样 `git log --oneline` 就成了一份按架构分区组织的变更历史。

## 6. 备选方案（记录为什么没选）

| 方案 | 描述 | 否决理由 |
|---|---|---|
| **A. ES Modules 多文件 + 无构建** | 拆成 `data.js` / `battle.js` / `ui.js`，用原生 `<script type="module">` | 🔴 **致命**：`file://` 协议下 ES Module 受 CORS 限制**无法加载**。前作有 `IS_FILE` 常量（L981），说明"双击打开"是明确支持的场景。此方案**直接摧毁核心分发优势** |
| **B. Vite + 打包成单文件** | 源码多文件，构建产出单个 HTML（`vite-plugin-singlefile`） | 🟡 技术上完全可行，是"标准答案"。否决理由：① 引入 Node/npm 依赖与版本维护 ② 源码与产物不一致，调试要靠 sourcemap ③ **用户是非专职程序员，构建链故障时无人可修** ④ 违反用户已拍板的约束。**若未来项目规模翻倍，这是唯一的升级路径**（见 §7） |
| **C. 多个 `<script>` 块（不用 module）** | 单文件内用多个 `<script>` 划分区域 | 🟡 前作正是这样做的（主块 + MMO 块）。**但它没有带来真正的边界**——两个块共享同一个全局作用域，`window.MMO = MMO` 就是明证。且它制造了 `00-singleplayer-migration.md` §S2 记录的那个 `ReferenceError` 陷阱（跨块裸标识符引用）。<br>✅ **部分采纳**：本作**只保留一个 `<script>` 块**，用注释分区替代物理分块 |
| **D. 拆成多个 HTML 页面** | 战斗页、背包页分开 | ❌ 状态在页面间无法共享，需序列化往返 localStorage，复杂度反而更高 |

## 7. 🔴 升级触发条件（何时应重新审视本 ADR）

单文件不是永恒正确。以下**任一条**成立时，应重开本决策并认真评估**备选方案 B**：

| # | 触发条件 | 现状 | 阈值依据 |
|---|---|---|---|
| T1 | 主 `<script>` 块超过 **8000 行** | 3541 行（本作预测 ~4400） | 经验阈值：超过此规模后全文搜索的信噪比会崩塌 |
| T2 | 单次功能改动需要在 **5 处以上分散位置**同步修改 | 目前最多 3 处 | 说明抽象已经失效，注释分区救不了 |
| T3 | 出现**第二位开发者**持续参与 | 单人 | N5 从"低"升级为"高" |
| T4 | 引入任何第三方库 | 0 依赖 | 一旦要引库，构建链的边际成本就降到很低了 |
| T5 | 数据表总量超过 **1500 行**且填表频繁出错 | 预测 ~600 行 | 此时应考虑把数据表外置为 JSON（**注意：`file://` 下 `fetch` JSON 同样受限**，需内联为 `<script type="application/json">`） |

> 📌 **本作 MVP 预测行数约 4900（主 script 约 4400），距离 T1 尚有约 45% 余量。决策在 MVP 与 V1 周期内保持有效。**
