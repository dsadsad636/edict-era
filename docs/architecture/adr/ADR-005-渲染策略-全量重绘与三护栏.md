## 1. 背景

### 1.1 前作的渲染形态（实测复核）

《守夜人·凋零纪元》采用**全量 `innerHTML` 重绘**：

| 入口 | 行为 | 频率 |
|---|---|---|
| `renderAll()` L3654 | `renderHeader()` + `renderNavTabs()` + `renderContent()` | 每次玩家操作 |
| `renderContent()` L3735 | `content.innerHTML = tabXxx()` **整个中栏字符串重建** | 同上 |
| `renderBattleScreen()` L4332 | `battleBody.innerHTML = ...` + `battleLog.innerHTML = 最近50条` | **每 650ms**（`tickBattle` 内） |

### 1.2 性能预算实测

| 指标 | 估算 | 判定 |
|---|---|---|
| 战斗屏重绘频率 | 650ms → **1.54 Hz** | ✅ 极低 |
| 单次重绘 DOM 节点数 | 战斗屏约 80-150 节点 | ✅ 小 |
| 背包满载重绘（600 件） | `invCell()` × 600 ≈ 3000 节点 | ⚠️ **唯一风险点** |
| 目标帧预算 | 单次重绘 < 16ms | — |

### 1.3 前作的分层违规（与 ADR-003 冲突）

在 `tickBattle()` L2568 中，`castSkill` 内 `pushLog` 后**直接调 `renderBattleScreen()`**——逻辑层**直接调渲染层**，违反 `01-main-architecture.md` §3.3 的单向分层（逻辑层只应打脏标记，由统一刷新点消费）。

更糟的是：前作一次玩家操作可能触发 **2-3 次 `renderAll()`**（`applyEquip` → `save()` → `renderAll()` 各处散调），既浪费又让渲染时机不可预测。

---

## 2. 决策

> ## ✅ **沿用「全量 `innerHTML` 重绘」，但加三个针对性护栏（P1/P2/P3）。**

**为什么不换成局部 diff 更新**：

1. 1.54 Hz 的重绘频率下，全量 innerHTML 的开销**远低于**引入 virtual-dom / diff 机制的复杂度成本。
2. 全量重绘是**天然正确**的——不存在"状态变了但界面没更新"这类 bug，对单人开发者是巨大价值（少一类最难调的 bug）。
3. 换成 diff 更新会**违反硬约束 3（骨架复用）**——等于重写渲染层。

### 2.1 三护栏

| # | 护栏 | 解决什么 | 成本 | 优先级 |
|---|---|---|---|---|
| **P1** | **背包虚拟分页**：每页 60 格，超出分页渲染 | 封住 600 件背包一次渲染 3000 节点的峰值（§1.2 唯一风险点） | ~30 行 | 🔴 **必须**（容量+性能双因） |
| **P2** | **脏标记 `markDirty(region)`**：逻辑层只打标记，渲染由 `requestAnimationFrame` 统一消费一次 | ① 修复 §1.3 的分层违规 ② 消除一次操作 2-3 次重绘的浪费 | ~25 行 | 🟡 **架构收益优先**（修复违规 > 性能） |
| **P3** | **战斗日志改增量 append**：`logEl.appendChild(新行)` + 超 50 行删首行，不重建 50 条 | 每 650ms 重建 50 个 DOM 节点 | ~15 行 | 🟢 可选 |

> 📌 **优先级说明**：P2 的**架构收益**（修分层违规、让渲染时机可预测）大于性能收益，应优先于 P3。P1 因容量与性能双重原因**必须做**。P3 在容量处置（ADR-002 / §6）已把日志移出存档后，纯属性能点缀，可延后。

---

## 3. 关键设计点

### 3.1 脏标记机制（P2 的核心）

```js
// 逻辑层只打标记，不直接渲染
function markDirty(region){ G._dirty[region] = true; scheduleRender(); }

// 统一刷新点：rAF 合并同一帧内所有脏标记，只刷一次
let _frameScheduled = false;
function scheduleRender(){
  if(_frameScheduled) return;            // 同一帧内多次 markDirty 只排一次
  _frameScheduled = true;
  requestAnimationFrame(()=>{
    _frameScheduled = false;
    const d = G._dirty; G._dirty = {};
    if(d.header) renderHeader();
    if(d.content) renderContent();
    if(d.battle)  renderBattleScreen();  // 战斗屏仍由 tick 触发，但合并日志增量
  });
}
```

**可接受的前提**：`_dirty` 是 `_` 前缀的瞬态字段（ADR-002 规则），**不入存档**，零成本。

### 3.2 背包分页（P1 的契约）

- 渲染层不再一次性 `invCell()×N`，而是 `invCell()×60` + 分页器（上一页/下一页/页码）。
- 背包上限 `INVENTORY_MAX=300`（§6.4 容量预算），300 件 = 5 页，峰值节点数从 3000 降到 **300**（60×5 中只渲当前页），**下降 90%**。

### 3.3 战斗日志增量（P3）

- `renderBattleScreen()` 内不再 `battleLog.innerHTML = 最近50条`，改为：
  - 新行：`logEl.appendChild(新行DOM)`；
  - 维护：若 `logEl.childNodes.length > 50`，`logEl.removeChild(logEl.firstChild)`。
- 内存日志上限 `LOG_MAX=200`（§6.4），页面只展示最新 50 条。

## 4. 备选方案

| 方案 | 说明 | 否决理由 |
|---|---|---|
| A. 引入 virtual-dom / diff 库 | 局部更新 | 🔴 违反硬约束 3（骨架复用）；1.54Hz 下收益可忽略；增加单人开发者的维护负担 |
| B. 保持前作散调 `renderAll()` 不变 | 最小改动 | 🔴 保留 §1.3 的分层违规与重复重绘；背包满载仍是性能悬崖 |
| C. ✅ 全量重绘 + 三护栏（本 ADR） | | 保留"天然正确"优势，补上唯一风险点与分层违规 |

---

## 5. 后果

| 类型 | 项 |
|---|---|
| ✅ 正面 | 保留全量重绘的"无状态不同步 bug"优势；P1 封住性能悬崖；P2 修好分层违规并消除重复重绘 |
| ⚠️ 代价 | 需新增 `markDirty`/`scheduleRender` 调度（~25 行）与背包分页组件（~30 行）；P2 要求逻辑层散调的 `renderAll()` 全部改为 `markDirty()` |
| 🔗 协同 | P2 的脏标记机制直接服务 ADR-003 的分层纪律；P1 的 `INVENTORY_MAX` 引用 §6.4 容量预算；日志移出存档由 ADR-002 C1 保证 |
| 🟡 风险 | P3（日志增量）延后到 V1 时，战斗屏每 650ms 仍重建 50 节点——但 1.54Hz 下无感，可接受 |
