## 1. 架构总览

### 1.1 硬约束（用户已拍板，本文档不重新论证）

| # | 约束 | 架构含义 |
|---|---|---|
| 1 | 纯单机，零服务端 | 唯一持久化出口 = `localStorage`；**架构中不存在网络层** |
| 2 | 单文件 `index.html` | 无构建、无模块系统、无 `import`；分层靠**约定**而非语言机制强制 |
| 3 | 骨架复用前作 | 不重写引擎；分层要**贴合前作既有形态**，不做理想化重构 |
| 4 | 文档先行 | 本阶段零代码 |

### 1.2 一句话架构

> **五层单向依赖 + 一个全局状态对象 `G` + 一个纯函数的派生计算层。**
> 数据层与逻辑层的边界是本架构唯一"用力"的地方（ADR-003），因为 79% 的开发工作发生在数据层。

### 2.4 分区约定（本作强制执行）

#### 规则 1 · 三级横幅体系

```
/* ################################################################
   §3  战斗层  BATTLE
   ################################################################ */

/* ==================== 3.2 伤害结算 ==================== */

/* ---- 3.2.1 命中判定 ---- */
```

| 级别 | 标记 | 用途 | 数量上限 |
|---|---|---|---|
| L1 章 | `####` + `§N 中文名 ENGLISH` | 五大层 + 数据层子章 | **≤ 12** |
| L2 节 | `====` + `N.M 名称` | 功能簇 | ≤ 8 / 章 |
| L3 目 | `----` + `N.M.K 名称` | 单个复杂函数内部 | 按需 |

#### 规则 3 · 编辑器折叠标记

在每个 L1 横幅后紧跟 `//#region §N` / 章末 `//#endregion`。VS Code / Sublime 原生支持，**整章可一键折叠**。这是把 4900 行压缩成 12 行可视目录的最低成本手段。

#### 规则 4 · 命名约定（用大小写编码"这是什么层"）

| 形态 | 含义 | 示例 | 可否被填表工作修改 |
|---|---|---|---|
| `全大写_下划线` | **数据表常量**（冻结，只读） | `MONSTERS` `SKILLS` `AFFIX_POOL` | ✅ **可以** |
| `PascalCase` | 命名空间对象（模块） | `Save` `Offline` `Render` | ❌ 不可 |
| `camelCase()` | 普通函数 | `genEquip()` `castSkill()` | ❌ 不可 |

| `G.xxx` | 运行时可变状态 | `G.player` `G.battle` | ❌ 不可 |

> ✅ 这条规则的实际收益：**"填表工作只允许修改全大写标识符的内容"** 成为一句可执行的一句话规则（ADR-003）。

### 3.2 各层职责契约

| 层 | ✅ 必须 | ❌ 禁止 | 违反的检测方法 |
|---|---|---|---|
| **§1 数据表** | 纯字面量；`Object.freeze()`；每表带 `// 字段契约:` 注释块 | 出现 `function`、`G.`、`Math.random()` | 章内 `grep "function\|G\."` 必须为空 |
| **§2 生成器** | 纯函数；所有外部输入**显式传参** | 直接读 `G.player`（例外见下） | 章内 `grep "G\."` 应趋近于 0 |
| **§3-4 逻辑层** | 唯一写 `G` 的地方；每次写完调 `markDirty()` | 拼接 HTML 字符串；直接操作 DOM | 章内 `grep "innerHTML\|getElementById"` 必须为空 |
| **§5 存档层** | 唯一 `localStorage` 出口 | 被 §7 直接调用 | — |
| **§7 渲染层** | 纯 `state → string`；只读 `G` | 出现 `G.xxx =` 赋值 | 章内 `grep -E "G\.[a-z]+\s*="` 必须为空 |

> ⚠️ **对前作现状的诚实标注**：前作 `totalStats()` L1968、`weaponPower()` L2052、`playerUnit()` L2427 **直接读 `G.player`**，不是纯函数。
> **决策：接受现状，不重构。** 理由：① 这三个函数是骨架复用的核心，重构风险 > 收益 ② 它们只**读**不**写**，仍然可测（构造一个假 `G` 即可）。
> 但**新写的生成器一律走显式传参**。这是"渐进收紧"而非"一次性重构"。

## 4. 状态管理：全局 `G` 对象设计

### 4.1 设计原则

| 原则 | 说明 |
|---|---|
| **单一真相源** | 除 `G` 外不存在第二个游戏状态容器 |
| **可序列化 = 可存档** | `G` 中凡是**可 JSON 序列化**的字段即为存档内容，**不需要单独维护存档字段清单**——这条规则消灭了"加了字段忘了存"这类 bug |
| **瞬态字段带 `_` 前缀** | `_` 开头的字段**序列化时剔除**（定时器 ID、DOM 引用、渲染缓存） |
| **运行时派生值不入 G** | `totalStats()` 每次现算，不缓存进 `G` |

### 4.2 `G` 结构

```
G = {
  /* ---- 元信息 ---- */
  ver: 1,                    // ✅ schema 版本号（ADR-002 的锚点）
  slot: 0,                   // 所属槽位 0/1/2
  createdAt, lastSaveAt,     // 时间戳

  /* ---- 角色 ---- */
  player: {
    name, level, exp, expNext,
    origin,                  // 出身 key（ORIGINS 的键，不存副本）
    str, agi, con, int, spi, attrPoints,
    hp, mp,                  // 当前值；上限由 totalStats() 派生，不存
    gold,
    materials: {lead, copper, silver, gold_, royal},   // 印屑
    equip:   {weapon, head, armor, hands, feet, ring, amulet},
    flasks:  {hp, mp},
    skills:  {<skillId>: level},
    inventory: [ Item, ... ]                            // ⚠️ 需硬上限，见 §6
  },

  /* ---- 世界进度 ---- */
  world: {
    mapId, mapTier, unlocked,
    encounter, eliteDone, bossDone, mapEliteAt, mapBossAt,
    autoChain
  },

  /* ---- 离线收益（🆕 见 02 文档）---- */
  offline: { lastActiveAt, lastSettleAt, monotonic, pending },

  /* ---- 图鉴（🆕 H4 预埋，MVP 只写不读）---- */
  codex: { kills:{<monId>:n}, seenItems:{<baseKey>:1} },

  /* ---- UI 偏好 ---- */
  ui: { navTab, folds:{}, bagCat, autoDecompose },

  /* ---- 瞬态（🔴 不序列化）---- */
  _battle: null,             // 战斗实例
  _battleTimer: null,        // setInterval id
  _log: [],                  // ⚠️ 战斗日志移出存档，见 §6
  _lastLoot: null,
  _dirty: {}                 // 渲染脏标记
}
```

### 4.3 🔴 与前作 `G` 的四处关键差异

| # | 前作 | 本作 | 理由 |
|---|---|---|---|
| 1 | 无 `ver` 字段 | **`ver: 1`** | 存档迁移的唯一锚点（ADR-002）。前作靠 `applyCompat()` 50 行 `if(typeof x==='undefined')` 盲补，不可持续 |
| 2 | `G.log` 300 条**进存档** | **`G._log`，不进存档** | 实测占 **31 KB/存档**。战斗日志是纯瞬态展示物，**没有任何理由持久化** |
| 3 | 世界进度平铺在 `G` 根 | 收进 `G.world` | 根对象从 ~20 字段降到 8 个，可读性 |
| 4 | `G.account{user,mode}` | **删除** | 随账号体系消失 |
| 5 | `battle`/`battleTimer`/`lastLoot` 无前缀但实际瞬态 | 加 `_` 前缀 | 前作靠 `applyCompat` L3630 手工清 `G.battle`——改成规则后自动生效 |

### 4.4 序列化规则（一行说清）

```
存档内容 = JSON.stringify(G, (k,v) => k.startsWith('_') ? undefined : v)
```

> ✅ 一个 replacer 函数就实现了"瞬态字段自动剔除"。加新字段时**不需要改存档代码**——这是 ADR-002 要解决的核心痛点。

## 5. 渲染策略

### 5.1 前作现状（实测）

**全量重绘 innerHTML**，无虚拟 DOM、无 diff、无局部更新：

| 入口 | 行为 | 频率 |
|---|---|---|
| `renderAll()` L3654 | `renderHeader()` + `renderNavTabs()` + `renderContent()` | 每次玩家操作 |
| `renderContent()` L3735 | `content.innerHTML = tabXxx()` **整个中栏字符串重建** | 同上 |
| `renderBattleScreen()` L4332 | `battleBody.innerHTML = ...` + `battleLog.innerHTML = 最近50条` | **每 650ms**（`tickBattle` 内） |

### 5.2 性能预算与实测判断

| 指标 | 估算 | 判定 |
|---|---|---|
| 战斗屏重绘频率 | 650ms → **1.54 Hz** | ✅ 极低 |
| 单次重绘 DOM 节点数 | 战斗屏约 80-150 节点 | ✅ 小 |
| 背包满载重绘（600 件） | `invCell()` × 600 ≈ 3000 节点 | ⚠️ **唯一风险点** |
| 目标帧预算 | 单次重绘 < 16ms | — |

### 5.3 决策

> ## ✅ **沿用全量重绘，但加三个针对性护栏。**（详见 ADR-005）

**为什么不优化成局部更新**：
1. 1.54 Hz 的重绘频率下，全量 innerHTML 的开销**远低于**引入 diff 机制的复杂度成本
2. 全量重绘是**天然正确**的——不存在"状态变了但界面没更新"这类 bug，这对单人开发者是巨大的价值
3. 违反硬约束 3（骨架复用）

**三个护栏**：

| # | 护栏 | 解决什么 | 成本 |
|---|---|---|---|
| **P1** | **背包虚拟分页**：每页 60 格，超出分页 | 600 件背包一次渲染 3000 节点 | ~30 行 |
| **P2** | **脏标记 `markDirty(region)`**：逻辑层只打标记，渲染由 `requestAnimationFrame` 统一消费一次 | 前作一次操作可能触发 2-3 次 `renderAll()`（`applyEquip` → `save()` → `renderAll()` 各处散调）；同时修复 §3.3 的分层违规 | ~25 行 |
| **P3** | **战斗日志改增量 append**：`logEl.appendChild(新行)` + 超 50 行删首行，不重建 50 条 | 每 650ms 重建 50 个 DOM 节点 | ~15 行 |

> 📌 P2 是**架构收益**（修分层违规）大于性能收益的一项，优先做。P1 是**必须**（容量与性能双重原因）。P3 可选。

## 6. 🔴 localStorage 容量风险评估

### 6.1 实测单体积（用真实 schema 构造 JSON 测量，非估算）

| 对象 | 字符数 | 说明 |
|---|---|---|
| **一件 4 词缀装备** | **405** | 含 `name`/`rarityName`/`base` 六字段/3 条含中文 `name` 的词缀 |
| 技能书 | 53 | |
| 药剂（2 词缀） | 190 | |
| **一条战斗日志** | **106** | `{side,text,time,hl,color}` |

### 6.2 前作 schema 下的容量推演

> **计费口径**：Chrome/Edge/Firefox 的 5MB 配额按 **UTF-16 计费，每字符 2 字节**（中文与 ASCII 同价）。
> 因此 **5 MB 配额 ≈ 2.6 M 字符**。以下"UTF-16 计费"列即为对配额的真实占用。

**单个存档：**

| 玩家画像 | 背包 | 单存档体积 | 其中战斗日志 |
|---|---|---|---|
| 轻度 | 50 件 | 54.5 KB | 31.1 KB（**57%！**） |
| 正常 | 200 件 | 113.8 KB | 31.1 KB |
| 囤积型 | 600 件 | 272.0 KB | 31.1 KB |
| 极端不分解 | 2000 件 | 825.7 KB | 31.1 KB |

> ⚠️ **第一个发现**：轻度玩家的存档里 **57% 是战斗日志**。这是纯浪费。

**⚠️ 第二个发现——槽位机制的体积放大：**

前作 `saveSlot()` L3204-3216 的实现是：**把所有 `SAVE_KEY::*` 的键做整体快照，塞进 `SAVE_SLOTS_KEY` 一个键里**。

这意味着 **N 个角色 × M 个槽位 = N×M 份全量副本**：

| 场景（前作 schema） | 总占用（UTF-16 计费） | 判定 |
|---|---|---|
| 1 角色 × 3 槽 | 0.89 MB | ✅ 安全 |
| 3 角色 × 3 槽（正常游玩） | 2.67 MB | ⚠️ 逼近 |
| **3 角色 × 3 槽（囤积型）** | **6.38 MB** | 🔴 **超出 5 MB 配额，`QuotaExceededError`** |

> 🔴 **结论：前作的存档 schema + 槽位机制在本作会撑爆 localStorage。必须处理。**
> 更糟的是 `setItem` 失败被 `try{}catch(e){}` L3212 **静默吞掉**——玩家会经历"存档看起来成功了，重开发现进度回退"，这是最恶劣的失败模式。

### 6.3 处置方案与效果

| # | 措施 | 效果 | 成本 |
|---|---|---|---|
| **C1** | **战斗日志移出存档**（`G.log` → `G._log`） | 每存档 **−31 KB**，轻度玩家存档直接**减半** | 🟢 0（改个字段名 + §4.4 的 replacer） |
| **C2** | **精简 Item schema**：删 `rarityName`（可由 `rarity` 查表）、删 `name`（可由 `equipName()` 重算）、词缀存元组 `["str",23]` 而非带中文 `name` 的对象、`base` 剔除 0 值、字段名缩写 | 单件 **405 → 189 字符，压缩 53%** | 🟡 中（生成器与渲染层各加一层 in/out 转换） |
| **C3** | **背包硬上限 300 件** | 封住无界增长。⚠️ **前作 `inventory.push()` 有 8 处，全部无长度检查——这是个真实的无界内存/存储漏洞** | 🟢 低（8 处加检查 + 满仓提示） |
| **C4** | **槽位只存元数据**，不存全量快照 | 消灭 N×M 放大。槽位 = `arcanum_save_v1::0/1/2` 三个独立键，`arcanum_slots_v1` 只存 `{name,level,origin,time}` | 🟡 中（重写 `saveSlot/loadSlot`） |
| **C5** | **写入前配额预检 + 显式失败提示** | 消灭静默失败 | 🟢 低 |

**处置后的容量：**

| 场景 | 处置前 | **处置后** | 改善 |
|---|---|---|---|
| 单存档（正常 200 件） | 113.8 KB | **39.1 KB** | −66% |
| 单存档（囤积 600 件） | 272.0 KB | **112.9 KB** | −59% |
| 3 角色 × 3 槽（正常） | 2.67 MB | **0.92 MB** | −66% |
| **3 角色 × 3 槽（囤积）** | **6.38 MB 🔴** | **2.65 MB ✅** | **−58%** |
| 3 槽 + 背包上限 300 | — | **1.35 MB ✅** | 配额占用 **27%** |

### 6.4 ✅ 最终结论

> ## **需要精简序列化，但不需要压缩算法。**

| 判断 | 理由 |
|---|---|
| ✅ **必须做 C1 + C3 + C4** | 成本极低（合计约 1.5h），三者合计就把最坏场景从 6.38 MB 压到 **1.35 MB**（配额的 27%），留出 3.7 倍安全余量 |
| ✅ **建议做 C5** | 静默失败是最恶劣的用户体验，`try/catch` 里必须给 toast |
| 🟡 **C2 可延后** | 做完 C1/C3/C4 后余量已充足。C2 会在生成器与渲染层引入 in/out 转换层，增加填表工作的心智负担——**与 ADR-003 的目标冲突**。列为 V1 观察项，等真实存档体积数据出来再定 |
| ❌ **不引入 LZString 等压缩库** | ① 违反单文件精神（要内联 ~4KB 压缩库）② 压缩/解压占用启动时间 ③ 压缩后的存档**不可人工读取与调试**，对单人开发者是净负债 ④ **在 C1/C3/C4 之后根本用不上** |

### 6.5 容量预算（写入 §0 CONFIG 作为可检查的常量）

```
BUDGET_SINGLE_SAVE   =  200 KB   // 单存档告警线
BUDGET_TOTAL         = 2000 KB   // 全部 localStorage 告警线（配额 40%）
INVENTORY_MAX        =  300      // 背包硬上限
LOG_MAX              =  200      // 内存内战斗日志上限（不入档）
```
每次 `Save.write()` 后检查，超预算打控制台 warn；超配额给玩家 toast「存档空间不足，请分解部分物品」。
