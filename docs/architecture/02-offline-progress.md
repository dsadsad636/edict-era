## 1. 设计目标与边界

| 目标 | 说明 |
|---|---|
| 留存钩子 | 玩家回来时有"攒了一笔"的确定性回报 |
| 契合支柱一 | 挂机 RPG 的自然延伸：离线也是"持牌者在外执法" |
| 实现成本极低 | 时间戳差值 × 收益率，核心逻辑 < 40 行 |
| ❌ 不做的事 | 不模拟离线战斗（不跑 tickBattle）、不产生离线掉落装备实体、不影响在线战斗循环 |

### 1.1 前作已有的时间戳先例（可复用的模式）

前作 `G.incenseUntil`（L1939 / L2823-2834）已经在用 `Date.now()` 做时间窗口：

```js
function incenseActive(){ return !!(G.incenseUntil && Date.now() < G.incenseUntil); }
```

✅ 说明骨架对时间戳持久化已有既定形态。本方案沿用同样朴素的风格，不引入新概念。

## 2. 时间戳存取方案

### 2.1 状态字段（`G.offline`）

```
G.offline = {
  lastActiveAt : <ms>,   // 玩家最后一次"确认在线"的墙钟时间戳
  lastSettleAt : <ms>,   // 上一次离线结算完成的时间戳
  monotonic    : <ms>,   // ⚠️ 单调累计在线时长锚（见 §3 防回拨）
  pending      : null    // 已算出、尚未被玩家领取的收益包
}
```

### 2.2 写入时机（`lastActiveAt` 的心跳）

| 时机 | 触发点 | 说明 |
|---|---|---|
| **周期心跳** | 复用前作已有的 20s 自动存档 `setInterval`（L3404） | ✅ **不新增定时器**——挂到既有的存档 tick 上 |
| **页面隐藏** | `visibilitychange` → `hidden`（前作 L3567 已有此监听） | 移动端切后台的主要路径 |
| **页面卸载** | `beforeunload`（前作 L3405 已有） | 尽力而为，不保证执行 |
| **手动存档 / 切槽位** | `Save.write()` 内 | |

> 📌 **20s 的心跳粒度意味着最多"丢失" 20 秒的在线时长**，会被错算为离线时长。
> 由于离线收益率必然 **远低于** 在线收益率，这个误差方向对玩家**不利但极微小**（20s × 低收益率）。
> ✅ 判定：可接受，不做补偿。**不要为此新增一个 1s 的定时器**。

### 2.3 读取与结算时机

```
启动流程：
  载入槽位存档
      ↓
  applyMigration(G)         ← ADR-002 版本迁移先跑
      ↓
  Offline.compute(G, now)   ← 纯函数，算出收益包，写入 G.offline.pending
      ↓
  渲染主界面
      ↓
  若 pending 非空 → 弹「归来结算」面板（见 §6）
      ↓
  玩家点「领取」→ Offline.claim(G) → 收益入账 → 清空 pending → save()
```

**为什么"算"与"领"分两步**：

| 理由 | 说明 |
|---|---|
| ① 崩溃安全 | 若在弹面板时浏览器崩溃，`pending` 已随存档落盘，重开仍能领到，**不会凭空蒸发** |
| ② 幂等 | `compute` 可重复调用而不重复发放（因为它写的是 `pending`，`claim` 才动 `player`） |
| ③ 可测 | `compute` 是纯函数，输入 `(G, now)` 输出收益包，**可以脱离 UI 单测** |

## 3. 🔴 系统时间回拨的处理

### 3.1 结论先行

> ## ✅ **要防，但只防"向前跳（刷收益）"，不防"向后跳"。用一行 `Math.min` 实现，成本近乎为零。**

### 3.2 判断依据

**"单机游戏是否需要防作弊"——这个问题问错了。正确的问题是"防它要花多少钱"。**

| 论点 | 分析 |
|---|---|
| ❌ 「单机作弊无害，玩家想改就改」 | **部分成立**。玩家开 DevTools 改 `G.player.gold=999999` 我们**完全无法阻挡**，也**不打算阻挡**。 |
| ✅ **但"改系统时间"与"开 DevTools"不是同一类行为** | 改系统时间是**在游戏外、无技术门槛、且可能是无意的**（跨时区旅行、系统对时、双系统启动、手机自动校时）。玩家可能**在不打算作弊的情况下**触发它。 |
| 🔴 **真正的伤害不是"玩家变强了"，而是"数值系统被击穿后玩家失去目标"** | 一次误触把 30 天收益一把领走，玩家的进度曲线被抹平，**游戏对他而言就结束了**。这不是道德问题，是**体验保护**问题。 |
| ✅ **成本论** | 完整防作弊（加密存档、校验和、可信时间源）成本极高且在单机下注定被绕过 —— ❌ 不做。<br>但**防"时间向前跳"只需要一个 `Math.min` 和一个单调计数器，成本 ≈ 5 行代码** —— ✅ 做。 |

> **一句话**：我们不做"防作弊"，我们做**"防误伤"**。花 5 行代码消除一整类"玩家莫名其妙进度崩了"的支持问题，这个 ROI 是压倒性的。

### 3.3 具体方案：三道闸

```
Δ_raw = now - lastActiveAt          // 原始墙钟差值
```

#### 闸 1 · 硬上限（主防线，同时也是设计上的离线上限）

```
Δ = min(Δ_raw, OFFLINE_CAP_MS)
```

**这一道就挡住了 99% 的时间前跳。** 玩家把系统时间调到 2099 年，也只能拿到 `OFFLINE_CAP_MS` 那么多——**与他正常离线一整个上限周期完全相同，作弊无收益**。

> ✅ 关键洞察：**离线上限本身就是最强的防回拨机制。** 它不是"额外加的防御"，而是"设计上本来就要有的东西顺便解决了安全问题"。

#### 闸 2 · 负值与荒谬值钳制（防时间向后跳）

```
若 Δ_raw < 0                        → Δ = 0，静默处理，不提示
若 Δ_raw < MIN_OFFLINE_MS (如 60s)  → Δ = 0，不弹结算面板（避免刷新页面就弹窗）
```

时间向后跳（玩家把时间调回去）只会让他**少拿**收益。
> ❌ **不惩罚、不报错、不提示"检测到时间异常"。** 玩家跨时区旅行不应该看到一句像指控的警告。静默钳制即可。

#### 闸 3 · 单调时长锚（补充防线，防"小步快跑"）

**闸 1 的漏洞**：玩家可以「+8h → 领取 → +8h → 领取」反复刷。虽然每次都受上限约束，但**次数不受限**。

```
G.offline.monotonic += 实际在线 tick 累计（每次 20s 心跳 +20000）

结算时：Δ_allowed = min(Δ, OFFLINE_CAP_MS, monotonic * OFFLINE_RATIO_CAP)
```

含义：**离线收益的累计总量，不能超过你实际在线时长的 K 倍**（`OFFLINE_RATIO_CAP` 由 GDD 定，建议 2-3）。
`monotonic` 只随真实的在线 tick 递增，**不受系统时间影响**——这是它作为锚点的价值。

| 玩家类型 | 闸 3 的影响 |
|---|---|
| 正常玩家（在线 1h / 天，离线 23h） | 若 K=3，可领 3h 等效 —— 但闸 1 的 `OFFLINE_CAP` 通常已经比这更严，**闸 3 不生效，玩家感知不到** |
| 时间前跳刷子 | 反复刷时 `monotonic` 不涨，**第二次开始收益趋近于 0** |

> ⚠️ **闸 3 的风险**：如果 `OFFLINE_RATIO_CAP` 定得太低，会误伤"周末才玩"的轻度玩家。
> 📌 **交付给策划的决策点**：`OFFLINE_RATIO_CAP` 的取值，或**是否在 MVP 启用闸 3**。
> 🟢 **我的建议：MVP 只做闸 1 + 闸 2（成本 5 行，覆盖 99% 场景），闸 3 留接口不启用**（`OFFLINE_RATIO_CAP = Infinity`）。若上线后观察到问题再打开——一个常量的事。

### 3.4 ❌ 明确不做的防护

| 不做 | 理由 |
|---|---|
| 存档加密 / 混淆 | 单机下必然被绕过；且**破坏存档可读性**，损害我们自己的调试能力 |
| 校验和 / 签名 | 同上；且校验失败时的处理（拒绝加载？）会误伤正常玩家的存档损坏场景 |
| 请求网络时间（NTP / HTTP Date） | 🔴 **直接违反"零服务端"硬约束**，不予考虑 |
| `performance.now()` 作为时间源 | 页面刷新即归零，无法跨会话，不适用 |
| 弹窗警告「检测到系统时间异常」 | 误伤跨时区玩家；且等于告诉作弊者"这里有检测，绕过它" |

## 4. 收益计算模型的接口定义

> 🔴 **本节只定义契约。所有数值常量由 `gdd/05-economy-loop.md` 填写，程序不擅自定值。**

### 4.1 常量契约（§0 CONFIG，等待 GDD 填值）

| 常量 | 类型 | 含义 | 归属 |
|---|---|---|---|
| `OFFLINE_CAP_MS` | ms | 离线收益累计上限（建议 8-12h 量级） | **GDD** |
| `MIN_OFFLINE_MS` | ms | 低于此时长不结算、不弹面板（建议 60-300s） | **GDD** |
| `OFFLINE_RATE` | 0-1 | 离线效率系数（相对在线收益率），**必须 < 1** | **GDD** |
| `OFFLINE_RATIO_CAP` | 倍数 \| `Infinity` | 闸 3 系数，MVP 建议 `Infinity`（不启用） | **GDD** |
| `OFFLINE_UNLOCK_LEVEL` | int | 解锁离线收益的最低等级（避免新手第一天就跳过教学） | **GDD** |

### 4.2 收益率来源契约 —— 关键设计

**问题**：离线时玩家在"打哪张图、用什么配装"？

> ✅ **决策：以"玩家上次离线前所在的地图 + 上次结算时的实测战力"为基准，不重新模拟战斗。**

```
G.offline.baseline = {
  mapId,            // 离线前所在地图
  mapTier,          // 该图 tier
  killRate,         // 实测击杀速率（只/分钟）—— 从在线战斗中滚动采样
  sampledAt
}
```

**`killRate` 的采样方式**（这是本方案唯一需要动战斗层的地方）：

```
在 endBattle() 的胜利分支末尾，追加一行：
    Offline.sampleKill(b.enemies.length, 本场耗时ms)

Offline 内部维护一个 EMA（指数移动平均）：
    killRate = killRate * 0.8 + 本次瞬时速率 * 0.2
```

| 为什么用实测采样而非公式推算 | 说明 |
|---|---|
| ✅ 自动包含全部变量 | 装备、技能、光环、套装、药剂、地图难度——**全部已经体现在实测速率里**，不需要在离线模块里重新实现一遍战斗公式 |
| ✅ 零重复逻辑 | 避免"离线公式"与"在线战斗"两套数值各自漂移（这是同类系统最常见的 bug 来源） |
| ✅ 自动惩罚"打不过硬撑" | 玩家在打不过的图挂机，`killRate` 自然趋近 0，离线收益自然趋近 0，**不需要额外写"能否通关"的判定** |
| ⚠️ 冷启动 | 新角色 `killRate` 为 0 → 由 `OFFLINE_UNLOCK_LEVEL` 兜底，未解锁前不结算 |

### 4.3 结算函数签名（纯函数）

```
Offline.compute(G, now) → OfflineReward | null

  // 纯函数：不修改 G，不读全局，只依赖入参
  // 返回 null 表示"不满足结算条件"（时长不足 / 未解锁 / killRate 为 0）

OfflineReward = {
  durationMs   : <ms>,     // 计入结算的有效时长（已过三闸）
  rawDurationMs: <ms>,     // 原始时长（仅用于 UI 显示"你离开了 X"）
  capped       : <bool>,   // 是否触顶（UI 提示"已达上限，建议早点回来"）
  kills        : <int>,    // 等效击杀数
  exp          : <int>,
  gold         : <int>,
  materials    : {<shardType>: n},   // 印屑
  flaskCharge  : {hp:n, mp:n}
}
```

```
Offline.claim(G, reward) → void
  // 唯一修改 G 的入口。内部复用现有 applyLoot() / gainExp()，不另写一套发放逻辑
  // 完成后：G.offline.pending = null; G.offline.lastSettleAt = now;
```

### 4.4 🔴 产出边界（明确不产出什么）

| 产出 | MVP | 理由 |
|---|---|---|
| 经验 | ✅ | 线性可算，无副作用 |
| 金币 | ✅ | 同上 |
| 印屑（材料） | ✅ | 同上 |
| 药剂充能 | ✅ | 同上 |
| **装备实体** | ❌ **不产出** | ① 会瞬间塞满背包，撞上 `INVENTORY_MAX`（见 `01` §6）② 一次性掉 50 件装备的"开箱"是**噪音而非乐趣**，违反支柱二的"减少无意义决策" ③ 生成 50 件装备要跑 50 次 `genEquip()`，启动时卡顿 |
| **技能书** | ❌ | 同上 |
| **Boss 唯一掉落** | ❌ | 终局内容必须由玩家亲手打出 |
| 地图进度推进 | ❌ | 离线不推图，不解锁新地图 |

> ✅ **替代方案**：离线产出的"本该掉落的装备"**折算成等价印屑**发放。
> 玩家拿印屑去「熔印坊」定向锻造 —— 这**把噪音（50 件白装）变成了决策（我要锻什么）**，同时给 MVP 唯一的金币/材料出口导流。
> 📌 折算比例交 GDD 定。

## 5. 离线上限与结算时机汇总

| 项 | 方案 |
|---|---|
| **离线上限** | `OFFLINE_CAP_MS`（GDD 定，建议 8-12h）。触顶时 `reward.capped=true`，UI 明确提示，**不隐瞒** |
| **最小离线时长** | `MIN_OFFLINE_MS`（建议 ≥60s）。低于此值静默跳过，**防止 F5 刷新弹窗骚扰** |
| **结算时机** | 存档载入 + 迁移完成之后、主界面渲染之前，只在**启动时算一次** |
| **是否在运行中重新结算** | ❌ **否**。页面持续开着不触发离线结算（即使标签页在后台）。理由：后台标签页的 `setInterval` 会被浏览器节流，但游戏逻辑仍在"在线"语义下，混用两种收益模型会产生双重计算 |
| **切换槽位** | 切换后对新槽位执行一次 `compute`（等价于"载入存档"） |
| **战斗中禁止结算** | 启动时 `G._battle` 恒为 null（瞬态字段不入档），天然不冲突 ✅ |

## 6. UI 呈现时机与形态

### 6.1 时机

```
主界面渲染完成（玩家看到自己的角色）
        ↓  延迟 ~300ms
   弹出「归来结算」模态
```

> ⚠️ **不要在白屏时弹**。玩家要先看到"我的角色还在"，再看到"我赚了多少"。**先确认安全，再给奖励**——顺序反了会让人下意识以为出了问题。

### 6.2 形态（叙事化，交美术总监与文策渊细化）

主题包装：**「巡回执法回执」/「离岗期间的查封记录」** —— 契合持牌者的世界观，把"挂机"叙事化为"在外执法"。

| 元素 | 内容 | 备注 |
|---|---|---|
| 标题 | 「巡回执法回执」 | 文案交文策渊 |
| 离开时长 | 用 `rawDurationMs` 显示真实时长（如「你离开了 14 小时 22 分」） | ✅ 显示真实值，不显示被 cap 后的值 |
| ⚠️ 触顶提示 | `capped=true` 时显示「**回执额度已满（上限 12 小时），建议早些回来**」 | 🔴 **必须诚实提示**。玩家发现"离开 3 天和离开 12 小时收益一样"却没人告诉他，会产生被欺骗感 |
| 收益明细 | 经验 / 金币 / 各色印屑 / 药剂充能，分项列出 | 复用 `applyLoot` 的展示组件 |
| 主按钮 | 「签收」 | 点击 → `claim()` → 入账 → 关闭 |
| ❌ 不做 | 「双倍领取」「看广告加成」 | 无变现需求，且违反支柱二 |

### 6.3 首次解锁提示

玩家达到 `OFFLINE_UNLOCK_LEVEL` 时，给一次 toast：「你已获得**巡回执法**资格 —— 离线期间将持续产生查封回执」。
让玩家**知道这个机制存在**，否则它对留存的价值减半。
